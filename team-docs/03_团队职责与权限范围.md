## 三、跨角色协作矩阵

当某个改动涉及多个角色时，以下矩阵定义了"谁发起 / 谁审批"：

| 改动场景 | 发起人 | 审批人 | 说明 |
|----------|--------|--------|------|
| 拆分 desktop_pet.py | A | 全员 | 巨型文件拆分影响所有人 |
| 新增 AI 后端路由 | C | A, B | A/B 的调用方需适配 |
| 新增 TTS 提供商 | B | C | config.py 需新增配置项 |
| 新增 Companion 传感器 | D | C | config.COMPANION_DEFAULTS 需扩展 |
| 新增桌面工具 | E | C | agent_client/deepseek_client 需注册工具定义 |
| 修改 IPC 命令格式 | E | A | renderer 进程（A 维护）需同步 |
| 修改 config.py 常量 | C | 对应依赖方 | 谁依赖谁审批 |
| 修改 route_and_send 签名 | C | A, B, D | 三方都依赖此函数 |
| 修改 storage APP_DIR | E | 全员 | 全局路径变更 |
| 修改打包配置 | A | E | A 管 UI 资源，E 管 build 脚本 |

## 四、代码提交规范

### 4.1 分支策略

```
main           ← 受保护，只接受 PR
├─ feature/A-*  ← A 的功能分支
├─ feature/B-*  ← B 的功能分支
├─ feature/C-*  ← C 的功能分支
├─ feature/D-*  ← D 的功能分支
├─ feature/E-*  ← E 的功能分支
└─ fix/*        ← bug 修复分支
```

### 4.2 PR 审批规则

| PR 涉及文件 | 必须 Reviewer | 说明 |
|-------------|---------------|------|
| 仅自己负责的文件 | 同角色另一人（若 solo 则跳过） | 自审 |
| 跨文件但同层 | 对方角色 | 跨文件 PR |
| 跨层 | 所有涉及层的角色 | 跨层 PR |
| 接口文档变更 | 全员 | 接口变更影响所有人 |
| config.py | C + 依赖方 | C 是 config.py owner |

### 4.3 提交信息格式

```
<type>(<scope>): <subject>

type:  feat | fix | refactor | docs | test | chore | build
scope: ui | voice | router | companion | infra | config | test | docs
```

示例：
```
feat(voice): 新增阿里云 TTS 情绪标签映射
fix(router): Ollama 分流失败未回退 local
refactor(ui): 拆分 desktop_pet.py 对话面板到 chat_panel.py
docs(infra): 更新 IPC 命令格式文档
```

## 五、冲突解决机制

### 5.1 文件归属优先

当两人同时修改同一文件时，**该文件的负责人有最终决定权**。

### 5.2 接口争议

当接口签名变更存在分歧时：
1. 在 `02_接口设计文档.md` 中标注 `[争议]`
2. 在 PR 中 @所有涉及方
3. 48h 内未达成一致 → 项目负责人裁决

### 5.3 紧急修复

生产环境紧急 bug：
1. 直接在 `fix/*` 分支修复
2. 通知文件负责人 review
3. 合并后由负责人在 `main` 上做回溯验证
